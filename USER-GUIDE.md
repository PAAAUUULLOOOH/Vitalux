# Vitalux user guide

## Start

Before the main window opens, a compact startup window follows the last selected design. The Vitalux circle, wordmark and activity line accompany a single real status message: hardware discovery, first sensor readings, product-cache loading or interface preparation. Widgets and first data are prepared before opening the dashboard. There is no artificial minimum wait; unavailable online information does not block startup. Motion-off and Ultra Eco keep the startup display and transition static.

Use the latest AppImage or extract the complete Linux ZIP and run `bash run.sh`. The source ZIP includes a compressed runtime too. Run `bash Portable-pruefen.sh` if a component cannot load. Keep the extracted program in its own writable folder.

## Monitor your system

Current Vitalux editions allow one running instance per user, shared across ZIP/AppImage copies and Stable/Unstable profiles. A genuine second start shows “Vitalux is already running.” During a marked restart, a short overlap waits for the old process to finish; a prolonged restart shows a restart-specific notice. Closing to the tray keeps that instance active; use **Exit** to quit. The lock is released automatically when the process exits or crashes, and normal renderer/update restarts remain supported. Older editions without this protection must be closed before opening another edition.

Reopening a sidebar category returns to its page start. The sidebar opens Overview, Processor, Graphics, Memory, Drives, Network, Sensors, Diagnostic Center, System, Settings, Updates and About. The new vector symbols remain recognizable when the sidebar is collapsed. Charts distinguish series by line pattern and identify measurements and timestamps on hover. Sampling interruptions appear as gaps; missing sensors are never replaced with invented readings.

On Overview, use the **Dashboard layout** grid button immediately left of Minimize to arrange cards. Its editing actions appear in the same top strip. Tiles stay stationary when editing opens. Their **Hold to move** captions and X controls stay visible throughout edit mode. Drives loads SMART data asynchronously. Start disk benchmarks or external diagnostics only when needed; writing tests temporarily create files on the selected drive.

Navigation follows the rounded window contour. Sidebar-only designs fill the left edge from top to bottom. Designs with a header integrate the window controls there; their sidebar joins directly below it. The extra dark window strip and duplicate distro/design captions are removed. The distribution remains in Overview. Cards scroll behind the fixed controls and header; the mouse wheel also works over these areas. In narrow header layouts, editing actions use icons with explanatory tooltips.

## Designs and backgrounds

Choose one of six rounded preview tiles under **Settings → Appearance → Design**: **Obsidian Gold**, **Glass**, **Crystal Atrium**, **Nebula Prism**, **Quantum Core** and **Light**. Obsidian Gold is the default for new profiles. Design changes retain your page, scroll position and running measurements. The selected check stays inside the tile's upper-right edge.

Every retained design supports preset/custom accents and backgrounds. Choose a retired design's original name in either selector to reuse only its colors or background. It does not restore the retired design's layout, materials or effects. Glass and Crystal Atrium are separate complete designs. Crystal Glass remains available as a color and background preset.

**Original colors** restores factory accents; **Original background** restores exactly the active design's factory backdrop without changing its accent. Choices are remembered separately for each design. **Reset design** restores only the current design's color/background choices; saved colors, imported images, other designs, motion and dashboard layouts remain intact. Own images still support Fill, Fit, Stretch, Center and Tile. The Sparkle background is animated; archived design backgrounds are static.

Crystal Atrium uses smooth glass surfaces on the shared window background. Its overview supports the same layout editor: move or hide tiles, restore hidden tiles, undo, discard or save changes. Nebula Prism retains its floating dock and prism instruments. Quantum Core retains its sidebar, angular panels and reactor instruments. Crystal Atrium uses its original static Atrium background; Quantum Core also stays static while logos and instruments follow **Animations**. **Ultra Eco** temporarily uses a plain skin, CPU rendering and a ten-second sample interval. Disabling it restores the last design and its saved appearance.

Overview headings, names and values are centered. The larger top card centers the distribution name relative to its entire width; a larger distro logo and larger system-information chips leave room for their text and move the remaining dashboard down. Component cards follow the same order: heading, load display, available name, details and supported watts. GPU overview omits watts; Graphics retains current watts and the limit. Long names are shortened with an ellipsis; hover over shortened text to read the full name. The load display keeps the same size when power measurements appear or disappear.

Toggle **Show component pictures** under Appearance to show or hide CPU, GPU, RAM and mainboard pictures together. With pictures off, no new picture searches start and cached images remain available for later use. Text and specifications remain centered whether a picture is visible, disabled or unavailable. The explanation beneath the switch describes this behavior.

## Processor history and datasheet language

Processor uses one chart card for usage, temperature and clock speed. Choose curves with the same checkboxes and 60-second / 5-minute / 15-minute controls as Overview. Each unit has a separate colored scale; hover over a sample for its actual value. Logical CPU meters remain below the chart.

Manufacturer datasheets follow the selected German or English app language, including open dialogs. Public manufacturer text is translated online using Microsoft Translator and cached per language. Local user/device details are not sent for translation; technical identifiers and quantities are preserved. Without a cached translation or an available translation service, Vitalux shows detected system data and a translated availability message, with the original manufacturer page still accessible.

## Apps and network connections

Open **Network → Apps & connections** to start the session monitor. Select an application to inspect its process IDs, executable path and TCP/UDP destinations. Running applications without current connections are also listed. Filter by name or path and sort by transfer rate or recorded usage. Connection details remain collapsed until needed. Totals cover the observed measurement session, not historical usage before Vitalux started. **Reset measurement** resets totals and warnings without changing active blocks.

The normal view uses Linux TCP diagnostics. UDP counters, inaccessible processes and unavailable kernel data remain unknown rather than being inferred from interface totals. Some containers expose connections but no per-socket byte counters. **Partial** means not all of an application's traffic could be measured. Live updates retain your selected app/connection and scroll position, including after a block or unblock.

**Authorize full measurement** sets up an isolated root-owned helper through Polkit, then requests authorization to use it. This optional feature needs cgroup v2, Linux cgroup BPF, process-fork tracepoints/perf events, Polkit (`pkexec`) and `/usr/bin/python3` on the host. If tracefs is not mounted, the helper accesses it in a private mount namespace without changing desktop mounts or global tracing settings. Missing kernel support or denied authorization is reported explicitly. The portable app itself still includes Python and runs without a system Python installation. Full mode measures TCP/UDP IP bytes, including protocol headers; changing measurement modes starts new totals because TCP payload and IP-byte counters are different measurements. No packet payload is captured.

Use **Block** or **Unblock** directly beside an application, or select it and use **Block network access** / **Allow network access**. Blocking requests Polkit authorization directly when needed; the status shows pending actions and errors. Select an application and expand **Advanced connections** to inspect its sockets. Select a TCP/UDP socket and use **Block connection** / **Unblock connection** to control that socket in both directions. An application-wide block takes priority over an individual socket rule. It covers running app processes and is inherited by their new subprocesses before they can open a connection. Python/Node script identities are kept distinct. Allowing an app releases its inherited blocks together. Rules last for the authorized session: **Release all blocks**, **End authorization**, closing Vitalux, or helper termination releases them. This is session traffic control, not a persistent firewall policy across reboots. Independently launched instances are discovered as the helper refreshes; treat blocks as controls for running processes, not as a security boundary against hostile software. Cached pages can remain visible in a blocked browser; verify with a fresh request.

**Usage warning** sets an observed-traffic threshold in MiB for each application (0 disables it). Vitalux shows the warning once per measurement session; reset measurement to start again. **Look up hostnames** explicitly asks the system resolver for PTR records. A PTR hostname does not verify who operates a destination.

## Settings search

Click the magnifier in Settings. Search grows with the text, adapts to the available width and shows matching settings. Clear predictions glide to the control automatically while you keep typing. Choose a result to focus its control; the search field then remains visible for five seconds and closes smoothly. Open, close and interrupted transitions remain smooth. Escape, an outside click or five idle seconds closes the field.

Partial names such as **Mini**, **MiniH**, **MiniHU** and **MiniHUD** predict the same section. Layout and opacity results have distinct labels; adding those words selects the specific control. Tied matches for one subject no longer suppress automatic navigation. Predictions preserve input focus and the selected language. A closed dropdown ignores the mouse wheel, so page scrolling cannot accidentally change a setting. Click sounds and their controls have been removed.

## Graphics and desktop overlay

**Advanced settings** is near the bottom of Settings, and contains the full **Restore defaults** action under Maintenance. Its contents are permanently visible; there is no expand/collapse action. It contains graphics rendering and **Maintenance** (full active-profile reset). Searching for these controls scrolls directly to the matching setting.

CPU rendering is the stable default. Experimental OpenGL, X11/OpenGL, Wayland/OpenGL and Wayland/Vulkan profiles depend on working drivers and a suitable session. Apply a renderer change with **Restart now**. Closing and restarting retain a responsive window until background work finishes safely. A failed startup falls back to CPU. X11 and Wayland select a window-system plugin; they do not change your desktop login session.

Vitalux Overlay for the desktop (formerly MiniHUD) reuses the main sensor stream and offers three layouts and adjustable opacity. Your desktop compositor determines its placement relative to fullscreen applications.


## Games and MangoHud

**Games** automatically reads installed games from native and Flatpak Steam libraries (including additional library folders), Heroic Epic/GOG inventories and Lutris. Discovery reads launcher data without changing it. Use **Scan again** after installing a game, or wait for the next one-minute scan. Search and page through the library; locally cached covers appear when available. No cover or telemetry uploads are made. Games with previous reports remain listed after uninstalling them.

MangoHud 0.8.4 is included for 32- and 64-bit OpenGL/Vulkan games in the AppImage, complete Linux ZIP and source ZIP. No separate MangoHud package or Flatpak extension is required. Vitalux keeps a private, versioned copy in its game-data directory; Flatpak launchers receive that copy in their own accessible data directory. Nothing is installed into the system and no Flatpak permissions are changed. Existing Vitalux game connections are refreshed automatically. The game's launcher, graphics drivers and normal game runtime remain required; driver/API, anti-cheat and launcher compatibility can affect overlays.

Select a game, open **Overlay profile**, then choose metrics, position, size, opacity, horizontal layout, shortcuts, recording delay and your target FPS. Close the launcher and select **Connect to launcher** once. Vitalux adds its persistent launch wrapper to the game's Steam launch options, Heroic wrapper settings or Lutris command prefix. Existing arguments and wrappers are retained. Heroic requires an existing saved game configuration; unfamiliar Lutris configuration formats are left untouched. **Remove connection** removes only Vitalux's managed prefix. Saving profile choices alone does not connect a launcher. Start through the launcher or **Start game** afterwards.

Keep Vitalux running, including in the tray, for automatic reports. MangoHud starts frame logging after the selected delay (default five seconds). Menus and loading screens count too; use the logging shortcut to pause/resume recording. The default shortcuts are right Shift+F12 for the overlay and left Shift+F2 for logging. Profile changes apply on the next launch. Turning off a game profile bypasses the wrapper while preserving the launcher connection. If the managed overlay files or configuration disappear, the original game command still runs.

After the tracked game processes finish and their logs settle, Vitalux opens that game's report. Average FPS is the number of valid frames divided by their total frame time. **1% Low** is the reciprocal of the mean of the slowest 1% of frame times; **0.1% Low** uses the slowest 0.1% and requires at least 10,000 frames. These definitions may differ from another tool's percentile method. The selectable FPS/frametime chart represents the whole session or its selected final time window; long charts retain frame-time extrema in a bounded display. Statistics use all accepted frames of the selected graphics executable. If a launcher and another graphics executable both produced logs, Vitalux uses the longest recording, combines its recording segments and names that executable in the report rather than mixing their FPS. Hardware peaks appear only for metrics actually reported by MangoHud.

Assessments compare the recording with its saved FPS target. **Very good** requires average FPS ≥99% of target, 1% Low ≥95% and at most 1% long frames. **Good** requires 90% / 70% / at most 3%; **Adequate** requires 70% / 45% / at most 8%. Other complete recordings indicate room for improvement. A long frame exceeds both 50 ms and twice the target frame budget. Sessions shorter than 30 seconds, missing frame data, sampled logs or incomplete recordings receive no overall grade. **Explain assessment** shows these criteria inside the app; they describe frame delivery, not hardware health.

Reports and profiles stay local and separate for Stable/Unstable. The latest 200 session reports are retained. Completed raw CSV logs have a 512 MiB budget; active logs are never pruned. Recording is limited to four hours, and analysis accepts at most eight million frames and 1 GiB per CSV; affected reports are marked incomplete. Startup imports finished logs left from earlier runs without presenting them as a newly completed game. Restoring default preferences resets overlay choices but retains reports and reversible launcher connections; their profiles return to defaults. Remove connections in Games before deleting Vitalux's game-data directory manually.

The desktop overlay remains available in **Settings → Overlay & window** and the tray. It uses the existing sensor stream. For FPS inside games and automatic game reports, use the MangoHud integration in **Games**.

## Reset settings

Section reset buttons softly appear when values differ from defaults and apply only to their group without restarting Vitalux.

The single full **Restore defaults** action is under **Advanced settings → Maintenance**. Advanced settings and Maintenance stay visible even with unchanged defaults or after a reset. Its description and confirmation list the consequences: reset all active-profile preferences, including design, accents, layouts, language, warning thresholds and graphics renderer; delete saved custom colors, imported background copies, profile cache and its automatic profile backups; restart the same Vitalux version and reopen the introductory guide. Original image files outside Vitalux and the other channel's profile/cache remain intact. Image-directory symlinks do not cause source images to be followed and deleted.

An active benchmark, diagnostic or update prevents the reset until it finishes. A failed defaults write restores the staged files. Fresh reset profiles remain initialized so Unstable does not copy Stable's preferences again. The separate cache and personal-preferences buttons are removed.

## Language and updates

Use **DE / EN** in the navigation area. Labels, the native guide, update notes and offline changelog follow the selected language without interrupting monitoring.

Vitalux checks the official release at startup and about every six hours. Read the current-language notes in **Updates**, then choose **Update now**. The full archive/AppImage and checksum must be available. AppImage replacement is atomic; a ZIP installation keeps its previous version for rollback. Personal data and settings are retained. Updates check free space before staging files and report interrupted downloads; a failed download does not replace the installed application. A centered percentage shows total preparation progress: downloading uses 0–80%, followed by verification and staging up to 100%. Slow connections report smaller received chunks. An idle socket times out after 15 seconds, subject to DNS and connection setup. When the server omits its size header, the official asset size or verified test manifest supplies the total. Progress stays at 0 until reception finishes only if neither source provides a size. **Cancel download** stops a transfer without activating the destination; a blocked read can take until its timeout to finish. **Retry download** starts a fresh verified transfer after a failure. Cancellation is unavailable once verification/preparation begins.

When Stable covers the installed or prepared Unstable build, the normal update automatically installs and starts Stable. This is checked again during preparation and before the automatic restart. There is no separate return step. Unstable becomes available again only when a newer test build exists.

The full release ZIP includes Python/Qt. Manual delta ZIPs are only for overlaying the immediately preceding portable ZIP version, never for AppImages. Keep a backup before a manual overlay.

## Troubleshooting

Normal settings: `${XDG_CONFIG_HOME:-~/.config}/vitalux`. Logs: `${XDG_STATE_HOME:-~/.local/state}/vitalux`. Diagnostic Center exports local reports; **About → Guide** opens the translated tour.

Explicit `Designs-testen.sh` previews keep their separate `design-test-data/` profile and disable releases. Use the normal `run.sh` or AppImage for update-enabled operation.

## Update channels and profiles

Everything stays in the **Updates** tab, without a channel-switch popup. The first card shows the installed channel/version once, its running status and **Check for updates**. The second card, **Update channels**, holds Stable/Unstable, their availability and release notes that always remain visible. Long notes scroll inside a bounded area; when the text fits, no scrollbar is shown. The version selector, progress and installation controls remain outside that text area. Its **Version** selector browses the selected channel’s release history, including offline notes; selecting another version starts its notes at the top. Older notes never change the installation destination or enable a downgrade; only the separate installation action prepares the latest verified destination.

Browsing does not alter your installed channel or create an update notification. A separate **Update now**, **Switch to Unstable** or **Return to Stable** action shows the target version and prepares the installation. The target appears only when installation is available, in progress or awaiting restart. Switching to Unstable requires a verified test build with real application changes beyond the current Stable baseline; otherwise its action is disabled with an inline explanation and its notes remain readable. Returning to Stable remains possible.

After a verified update or channel switch is prepared, Vitalux automatically finishes background work and restarts into the selected build. The prepared destination remains fixed; browsing other notes cannot change it or offer the package twice. The previous process fully exits before an external helper activates the ZIP/AppImage and reopens it once. If helper preparation fails, monitoring resumes and preparation retries automatically, with up to three attempts. Only a persistent failure shows **Retry restart**. A valid saved preparation resumes automatically on a later launch. The verified destination remains fixed, and an activated helper is never launched twice. Restart outcomes are recorded in `restart-events.jsonl` beside the pending-update state for local diagnosis. Upgrading from v0.9.6.2 still requires its older **Restart now** action once. The current Stable updater handles later verified updates and channel switches automatically; deliberately returning to an older edition also restores that edition's updater behavior.

Stable keeps its existing preferences. Unstable automatically creates a separate profile on first launch using Stable's preferences and imported backgrounds. Subsequent launches, updates and switches preserve each profile; migrations receive local backups (the latest five per channel). Profile handling is automatic: there is no import or fresh-profile button, and switching back never overwrites the other channel's preferences.

When a fresh verified catalog confirms that Stable contains all changes in the installed Unstable build and no separate test offer remains, Vitalux automatically prepares the verified Stable package and restarts into Stable. Cached notes, unavailable metadata and a shared base-version number alone cannot trigger this return. New test builds require an explicit manual switch back to Unstable. A newer eligible Unstable build takes precedence. A single rolling prerelease supplies test packages; when it has caught up with Stable it is marked **Unstable — based on Stable v…**, without creating another mirror build or consuming another test number. GitHub's **Latest** download always remains Stable. Technical test versions are retained internally for correct ordering and recovery.

Channel changelogs are cached for offline reading with their check time. Offline or failed checks are reported explicitly; cached information alone cannot authorize an installation.

**Recent events:** the Diagnostic Center shows the latest five app warnings, update failures and automatic renderer fallbacks. Entries remain local and follow DE/EN. Repeated identical events are grouped briefly; the optional Blackbox remains separate. Known causes of missing CPU/GPU readings appear as short labels; unknown causes remain unavailable.

**Logs:** Vitalux keeps an active file and one previous file per log, rotating at about 5 MB (roughly 10 MB combined, allowing complete error records). This includes launcher, crash, installation, restart and local event logs. Stable and Unstable use separate directories. Crash recording and automatic version recovery remain active.

## Hardware identities and product pictures

**Processor** lists all present logical CPUs in numerical Linux CPU-ID order, including offline entries. Its meter grid changes columns with the available width and grows vertically, so every entry remains reachable. Manufacturer and model come from the available CPU information. Its header contains short specifications; supported CPU power readings are shown on the overview. PL1/PL2 power-limit rows have been removed from the Processor card.

**Graphics** separates the GPU designer from the board manufacturer. Vitalux combines driver-reported names, PCI/subsystem IDs and a bundled general PCI database; unresolved IDs can refresh that database online. Shared IDs retain the available GPU description rather than guessing a partner edition. **System** uses readable DMI manufacturer, model and revision fields for the mainboard. Internal model suffixes and differing vendor spellings are normalized for picture searches without changing the reported model.

**Memory** adds manufacturer, part number and short module specifications when readable SMBIOS memory-device records are available. An installed `dmidecode` can provide the same data without changing system permissions. Firmware may leave fields blank, and access to its tables is restricted on some machines. In those cases the ordinary memory measurements remain available. Different module products remain separate; Vitalux does not infer a retail kit from its capacity or substitute a memory-chip vendor for a reported module brand.

CPU, GPU, memory-module and mainboard headers center their identity and specification text across the card, with a matching product picture above when available. Real cutout images are preferred. When no matching cutout is found, a matching photograph with its original background is accepted instead, including valid pictures cached by older versions. CPU images require an image-level model match; uncertain older CPU cache entries are rechecked. Without any matching picture, the image column and its spacing disappear: the name and specs remain centered across the card. White hardware is never made transparent by blanket color replacement.

CPU, graphics-card and mainboard headers offer **All specifications**. The native dialog groups all available manufacturer specifications into scrollable sections and includes **Open manufacturer page** for the original. The source date and selected display language are identified. Manufacturer text follows the app language and its translation is cached separately. The exact detected model is matched before data is accepted; saved results remain available offline. Local detected values are shown separately. If the manufacturer page cannot be read, the dialog reports that and keeps the actual detected information available. Available source data determines completeness.

Pictures are looked up in background workers using manufacturer model routes, product pages, headings, SKU/MPN metadata, image galleries/CDNs and online search. CPU generation/clock suffixes and internal mainboard codes are normalized without dropping model variants. Initial uncached searches send manufacturer/model terms to Bing or DuckDuckGo; serial numbers are not included. A valid background alternative can appear immediately while the worker continues looking for a cutout. Accepted pictures are cached persistently in the active profile and load again after restart without Internet access. There is no visible offline-cache status. Visible failed searches can retry after at least a minute; revisiting the page also permits retry. Bounded lookup diagnostics are kept alongside the profile's hardware-product cache. **Restore defaults** clears the active profile's cache, preserving the other channel.

Right-click a component header to **Reload component data**, **Discard incorrect picture**, **Choose a component picture** or view lookup details. These actions affect only that component. Rejected image URLs are excluded from future searches; a local picture is copied into the active profile and remains available offline. Refreshing returns to automatic lookup.

With several GPUs, **Preferred graphics card** selects the device used by the overview, desktop overlay, alerts and diagnostics. All GPUs retain their own histories and remain visible on Graphics. An unavailable preference falls back to the first available GPU.

## Hardware sensors and measured power

Overview tiles show only the current measured power, for example **Power: 85 W**, for CPU, memory and the system drive where supported. GPU watts appear on Graphics. The system-drive value requires an unambiguous sensor association with the mounted root device. Missing readings leave no power row; zero watts remain visible.

Processor combines load, temperature and clock speed in one selectable history with separate unit scales. Graphics places utilization and video-memory readings with the other **Current GPU values** and removes the duplicate sensor panel. Its history still shows load and video-memory usage together; **Technical details** contains the separate temperature and clock histories. Memory shows RAM usage, while Drives and Network show their original transfer-rate charts. Use each chart's visible checkboxes to choose its existing curves and select a 60-second, 5-minute or 15-minute window. Selections and time windows are saved separately for each page and GPU. Each chart retains its own physical unit. Right-click a live source-backed value for copyable source details. Sensor and System pages list their live readings without the added combined chart. The Sensors page retains distinct sensor IDs even when labels match and has no fixed 80-reading limit. Sampling failures show an explicit outdated-reading notice; history resumes with a gap. The diagnostic Blackbox distinguishes missing readings from a real return below a warning threshold.

Graphics keeps current power and its readable numeric limit with the other live values. There are no additional watt charts or average/peak power blocks. Missing sensors stay hidden, genuine zeroes stay visible, and GPU histories keep device identity and gaps even while visiting other tabs.

CPU package and DRAM power use readable RAPL/powercap energy counters and actual elapsed time. Driver-reported power constraints may remain available separately in Sensors when supported. First samples, resets, invalid intervals, suspend and unreadable counters require a new baseline. Existing Linux permissions apply; do not run the GUI as root. If openSUSE restricts RAPL access, those measurements stay hidden until the system administrator provides appropriate read access.

AMDGPU uses DRM/hwmon and explicitly supported gpu_metrics revisions. GPU edge, hotspot and memory temperatures, RPM, voltage, memory-controller activity and video-engine activity are distinct readings. VRAM occupancy is not memory-controller load; combined VCN activity is not presented as separate encode/decode activity. Unrecognized metric layouts and unsupported fields are skipped. NVIDIA adds driver-reported limits, memory temperatures, encoder/decoder activity and available limiting reasons through nvidia-smi. AMD's ASIC-independent limiting flags remain raw driver flags rather than guessed causes.

Board/VRM, fan, voltage, RAM/DRAM, storage, network and other device readings appear only where their drivers expose real sensors. RAM, SSD and PSU watt measurements are not universally available. CPU package, CPU subdomains, GPU socket and individual rails can overlap: Vitalux keeps them separate and does not add CPU plus GPU into a PC-total estimate.

A disappearing sensor immediately loses its current field; remaining fields reflow without empty slots. Genuine zeroes such as 0 RPM or 0 W stay visible. Recovered readings resume without bridging unavailable intervals. The full running app version in Updates remains unchanged while browsing versions or downloading an update; it changes after the new app starts.

The graphics overview tile shows the complete GPU name with line wrapping and has no watt caption. Its load display keeps the same size as the other overview instruments; long names add text space instead of shrinking the meter. Current GPU power and power limit remain in the Graphics page.

Diagnostic report text follows the selected German or English interface language, including export. Raw output from system tools remains unchanged. Saving a ChangeRadar baseline runs in the background. Network error details have an explicit copyable view; hidden network pages keep collecting traffic and warnings without rebuilding tables. Update progress remains monotonic when a verified promotion requires a second package download.

## Window controls

The main window has rounded outer corners and its own minimize, maximize/restore and close buttons. Designs with a header integrate these controls directly into it; sidebar-only designs show them over the window background without an extra tinted strip. Drag a free area beside the controls to move the window; double-click it to maximize or restore, or right-click for window actions. Drag an edge or corner to resize. Content scrolls behind the fixed controls/header, and the wheel works over these areas. Navigation fills the window contour without duplicate distro or design captions. The buttons are keyboard-accessible, and desktop window shortcuts retain their configured actions. Maximized and full-screen windows fill the display without rounded corner cutouts. The close button follows **Keep running in the system tray**; the tray’s Quit action still exits the app.

Overview cards use the available width with even outer margins, adapt to window resizing and sidebar width, and start close below the top controls. Expanding or collapsing the sidebar animates only its content row, keeping window controls and fixed design navigation in place.

The initialization card stays centered as the display becomes ready, including compositor-managed Wayland placement. Only the small rounded card is visible; its position also follows display geometry changes during login.
